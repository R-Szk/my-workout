> **実装担当者向け:** 承認後は superpowers:executing-plans を使用し、各タスクをテスト先行で進める。チェック項目は承認前には実行しない。

**目的:** 筋トレの知識が少なくても、自宅でアプリに沿って10〜15分取り組め、記録と写真から変化を振り返れるようにする。
**構成:** 単一appモジュール、Kotlin・Compose・MVVM・Room・Material 3を継続。記録処理と種目定義・表示素材を分離し、旧ジム記録を保持したまま自宅用の6種目とA/Bを追加する。
**技術:** 既存のバージョンとminSdk 36を維持。試作はCompose Canvasと既存のアニメーションAPIを使い、外部アニメーションライブラリは追加しない案。
**仕様:** 2026-11-08のユーザー依頼を優先。旧docs/design.md・docs/implementation-plan.mdと矛盾する部分は、本案の承認後に改訂する。

## 2. 共通条件と画面方針

- 端末内・オフライン。破壊的移行、旧記録削除、既存メニューの無断上書きを禁止。
- 週2〜3回、1回10〜15分は目安。1種目や1セットで終了しても正常終了として保存する。完遂や連続日数を要求しない。
- ホームはA/B・開始／再開・履歴を中心にする。「今週○回」と穏やかな目安を表示し、未達・連続途切れを赤字や警告で評価しない。
- 記録画面は上から種目名、アニメーション＋独立した筋肉図、今日の目標と前回、入力・完了セット、固定の「Nセット完了」。Nは保存済み数＋1。
- 筋肉図は常時表示。小画面・横画面・IME表示では画像を縮小し、入力と操作はスクロールできる。主要ボタン56dp以上、操作領域48dp以上を維持。
- 「フォームのコツ」は1〜2行を常に表示し、詳細は「詳しく見る」で展開。専門的な筋名の詳しい凡例は図の拡大時に表示する。
- 「スキップ」と「今日はここまで」を直接操作できるようにする。途中まで記録済みなら「残りをスキップ」として保存済みセットを残す。全体を未実施に変えて実績を隠さない。
- セットの直接編集・キャンセル・取り消し、当日の順番変更・種目追加を維持。不要な説明行を再導入しない。

## 4. データモデルと移行案

### 変更案

既存テーブルを全面改名せず、Machineを内部の互換モデルとして残す。画面とドメインでは「種目」と呼び、ExerciseDefinitionへ変換する。IDを名前で判定したり、旧ラテラルレイズをダンベル種目へ置換したりしない。

| 保存先 | 追加・変更する情報 |
|---|---|
| Machine | nullableなcatalogKey（home.push_up等の一意キー）、environment（GYM/HOME）、recordingMode（BODYWEIGHT/EXTERNAL/ASSISTANCE）、sideMode（通常／左右各）、非表示フラグ |
| Routine | 自宅A/Bを識別する一意catalogKey、environment、通常選択からの非表示フラグ |
| RoutineExercise | targetRepsMin / targetRepsMax、nullable targetWeightKg。既存targetRepsを今日の基準値として継続 |
| SessionExercise | 種目キー・記録方法・左右の扱い・回数範囲・目標重量を開始時にコピー。旧visualKeyと名前は維持。remainingSkipped（既定false）で残りだけのスキップを区別 |
| SetRecord | weightKgをDouble?へ変更。自重はnull、外部負荷は正数。既存id / sequence / completedAt / requestId / repsは保持 |
| 新規AppSettings | ホームで選ぶ環境・直近メニュー、プリセット適用バージョン。Roomで保持し設定専用ライブラリは増やさない |
| 新規EquipmentSettings / EquipmentWeight | ダンベル1個分の最大重量（未登録はnull）と実際に使える重量候補。候補は整数グラムで保存し重複を除く。20〜30kgを確定値として登録しない |

- BODYWEIGHTでは重量入力を表示せず、未入力のnullで保存する。0kgや体重推定を代入しない。ダンベルと旧ジムの0kg拒否は維持する。
- 一部実施後のスキップはremainingSkipped=trueにし、実績のある行をSKIPPEDへ変更しない。restoreで残りのスキップも解除する。既存集計のSKIPPED除外によって実施済みセットが消えたように見えることを防ぐ。
- 完了状態は従来どおりSetRecordの存在で表現。未完了の予定行はDBへ保存せず、スキップ状態はSessionExerciseに保存。実績と予定を混同しない。
- 旧ジムの種目・実績は旧IDのまま。旧0kg記録が存在しても削除・自重への再分類はしない。
- 新規インストールは自宅6種目と新A/Bだけを登録する。旧SeedCatalogは移行／旧履歴の参照用として保持し、新規初期化時に旧9マシンを再登録しない。
- 自宅カタログの数値IDは既存IDと衝突しないよう割り当て、一意catalogKeyで繰り返し起動時の重複を防ぐ。A/BはID=1/2ではなくキーと環境で取得する。
- 比較は種目キー＋実施バリエーション＋記録方法＋左右／重量単位の条件で行う。旧ジムカールとダンベルカールを同種目として連結しない。
- ワンハンドローは「左右それぞれ○回」を1セットとして保存し、「左右ともNセット完了」と表示する案。片側だけで完了したと誤解させない。
- 重量は全ダンベル種目で「1個あたり」と明示する案。トライセプスは1個を両手で持つ方式を初期案とし、カール試作後の種目展開時にフォームを確定する。持ち方を変更する場合は別バリエーションとして比較を分ける。
- カスタム種目も同じ定義を使用。説明・アニメが未登録でも記録可能だが、誤った他種目の動作を代用しない。

### v4→v5の保護策

1. テーブル追加・列追加に加え、set_recordsの重量nullable化には明示的Migrationを用意。新テーブルへのコピー、外部キー・一意インデックス・ID・自動採番継続を検証する。destructive fallbackは禁止。
2. 旧レコードの重量・回数・並び・日時・requestId・スキップ・中断位置・編集済み名称をそのまま保持。旧SessionExerciseの追加列は旧仕様相当の値で埋める。
3. スキーマ移行後、自宅6種目と新A/Bを一度だけトランザクション登録。seedIfEmptyだけに依存しない。旧テンプレートは保持し通常選択から外す。
4. 進行中のジムセッションを勝手に終了・変換しない。旧画面で再開／終了でき、終了後の通常開始を自宅A/Bにする。
5. 再実行しても新A/Bのユーザー編集を上書きしない。途中失敗ならDB更新をロールバックする。

## 5. 新しいA/B

全種目2セット。指定された回数範囲を保持し、初回の今日の回数は範囲の下限を提案する。ダンベル重量は未設定で開始し、実際の重量を選んだ後は前回値を優先する。種目・順序・セット数・回数・重量は後から変更可能。

| メニュー | 順番・種目 | 回数範囲 | 主な対象 | 重量 |
|---|---|---|---|---|
| A：胸・肩・二の腕 | 1 プッシュアップ | 8〜12 | 大胸筋 | 入力なし |
| A | 2 ダンベル・サイドレイズ | 10〜15 | 三角筋中部 | 1個分 |
| A | 3 ダンベル・トライセプスエクステンション | 8〜12 | 上腕三頭筋 | 1個分 |
| B：背中・力こぶ・下半身 | 1 ワンハンド・ダンベルロー | 左右各8〜12 | 広背筋 | 1個分 |
| B | 2 ダンベルカール | 8〜12 | 上腕二頭筋 | 1個分 |
| B | 3 スクワット | 10〜15 | 大腿四頭筋・大臀筋 | 入力なし |

「メニュー編集」は今後の既定値、「今日の目標変更」は進行中のセッションだけを変更する。過去の実績や開始済みの別セッションへ遡及しない。目標セット数を既存完了数より少なくしても実績は消さない。
器具の上限と重量候補は後から登録可能。未登録時は手入力、登録後は＋／－で実在する隣の重量へ移動する。最大重量だけから存在しない重量候補を生成しない。

## 6. カールアニメーションの方式比較

| 方式 | Composeとの関係・長所 | 品質・保守上の負担 | 判断 |
|---|---|---|---|
| Compose Canvas＋部位別ベクター＋角度補間 | 既存APIで描画・再生状態を制御。外部runtime不要。肘・手首の位置を数値テスト可能 | 人体の輪郭、重なり、見え方の作り込みを自前で行う。複雑な動作は制作負荷が増す | 最初の1種目に推奨 |
| Lottie Compose | Compose用APIとローカルJSON再生があり、制作済みの滑らかなベクターアニメを表示できる | アニメ制作・書き出し工程と依存追加が必要。素材がない今はJSON再生だけ導入しても品質は得られない | Canvas試作で表現不足なら比較対象 |
| Rive | .riv素材とAndroid runtime、状態制御の仕組みがある | 専用素材の制作・エディター・runtimeの管理を追加する | 現在の1種目試作では採用しない案 |

この推奨は構成と制作負荷からの判断であり、参考画像相当の品質を達成済みという意味ではない。静止画2枚交互、画像全体の回転、棒人間だけで完成とする案は採用しない。

### 最初の試作品の仕様

- DB・A/Bを変更せず、デバッグ用の独立した試作画面にカール1種目だけ表示する。
- 参考の体格・服装・髪・靴を踏まえたオリジナル2Dキャラクター。透明背景。腕の軌道が読める斜め前の視点を候補とし、別デザインとして確定する前に試作品で確認いただく。
- 胴・上腕・前腕・手・ダンベルを別の図形として持つ。肘の基準点と上腕を固定し、前腕・手・ダンベルがつながって動く。手首が折れたり、胴や肩を振って持ち上げたりしない。
- 1往復2.5秒を初期案とする。開始→曲げる→戻すを連続補間し、折返しとループ境界で位置・速度が跳ねない。各部の前後関係もフレームごとに保つ。
- 入場時に自動再生。タップでその位置に停止／再開し、再開時に開始ポーズへ飛ばさない。画面外・バックグラウンドでは描画更新を停止する。ユーザーが停止した状態は復帰だけで解除しない。
- アニメと筋肉図は別部品。透明領域を保ちFit表示し、靴・頭・ダンベルを切らない。
- 軽量性は実測する。試作前後のAPKサイズ、フレームの引っ掛かり、画面外の更新停止を確認して報告する。未計測のサイズやFPSを保証しない。
- 開始／中間／終了の静止画と操作動画で、見た目・肘・軌道・滑らかさを確認いただく。承認前に残り5種目の素材制作へ進まない。

## 7. 筋肉図・成長・目標提案

- BodyMapの前後の輪郭を再利用。自宅6種目の主／補助筋をHomeExerciseCatalogに定義し、写真やアニメのファイル名から推測しない。主ターコイズ（候補#2DD4BF）、補助の淡色（候補#99F6E4）、対象外グレー。
- 旧赤／オレンジPNGを自宅筋肉図に流用しない。主な対象は依頼の表のとおり。補助筋と動作フォームは一次資料で照合してから確定する。
- 自重グラフは回数を中心にし、重量nullを0kgに変換した重量グラフを作らない。ダンベルは重量と同じ重量での回数を表示。旧ジム履歴と比較条件を分離する。
- 前回の実績を入力初期値にし、その横に「次は○回も試せます」と任意の提案を表示する。前回値を勝手に提案値へ置き換えて保存しない。
- 次回回数は前回の代表セットの回数＋1を目安に、その種目の上限まで。初期基準: 同じ重量で、直近2回の終了済みセッションとも設定セット数を満たし、各セットが上限回数以上なら重量アップ候補を提示。
- 重量アップは登録済み候補の次の重量だけ。未登録・最大到達なら増量提案をしない。採用時の回数は範囲下限を候補にし、採用・維持・減量は自由。自重種目にダンベル増量提案を出さない。
- 一部種目・少ないセットでの終了も月間実施回数として従来同様に集計する。0セットやスキップだけでは回数を水増ししない。
- 写真比較とバックアップは下記の独立した後続段階。写真比較は自動体型判定を追加せず、2時点を並べて見られることに絞る。

## 10. 想定課題と承認対象

- **人体の動きの品質:** ベクターと補間ができても正しいフォームにはならない。カールで絵柄・視点・肘・軌道を実物確認し、品質不足ならLottie等を再比較する。残り5種目を先に作らない。
- **素材の不足:** 参考PNGはあるが透明レイヤー／原画／アニメ素材はない。オリジナル制作が必要。参考画像そのものの同梱・公開は行わない。
- **記録の意味:** 1個分の重量、左右各、両手で1個を持つ種目、自重を区別しないと誤比較になる。提案した単位と持ち方は承認対象。
- **移行と未完了記録:** 新種目へ上書きせず、自宅プリセット追加と旧履歴保護を両立する。カタログ再登録で利用者の編集を消さない。
- **10〜15分:** 目安であって強制終了時間ではない。左右の実施や任意の休憩、編集したセット数で延びても利用を妨げない。
- **器具未設定:** 初回に全重量一覧を入力させない。最大値も刻みも推測せず、登録前は手入力で継続できるようにする。
- **写真と復元:** 現在存在しない機能なので、簡単なUI変更の一部として完了扱いにしない。後続段階で安全なファイル管理と移行テストが必要。
- **作業ツリー:** 直近の未コミット修正とユーザーのステージ済み参考PNG／manifestを保持する。今回の計画承認をコミット／GitHubプッシュの指示とは扱わない。

承認いただきたいのは、(1)最初はDB変更なしのカール試作だけ、(2)試作承認後のv5移行と自宅6種目、(3)重量は1個分・片手ローは左右各、(4)Canvasをまず試す、という方針。試作動画確認後に残りの実装段階へ進む。
